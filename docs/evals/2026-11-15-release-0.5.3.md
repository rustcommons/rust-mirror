# 0.5.3 security release candidate — 2026-11-15

## Authorization and source boundary

The owner authorized 0.5.3 through Trusted Publishing after coordinator review and
merge. The source base is main 7e0b9aae6752f4102fac5435ca46d317aecbb0f7, the normal
merge of security-baseline PR #51. Main CI 43770690009 and security gates
43770690016 passed; Scorecard 43770689989 also completed successfully on that merge.
No new application implementation, dependency identity or workflow changes are
introduced by release preparation. The manifest and lock change only the root
version from 0.5.2 to 0.5.3; src/, examples/, scripts/, tests/ and the shim match main.

[Versioned notes](../releases/v0.5.3.md) identify all eleven upstream RustSec
advisories and their available GHSA aliases, the conservative <=0.5.2 locked/prebuilt
upgrade range, exposure observations and limits. The changelog, install guidance,
owner authorization and ROM-REQ-060 change together. Previous notes/registry payloads
and binary profiles remain immutable. A repository advisory is drafted privately;
only the coordinator publishes it after the software release.

## Primary-source and exposure checks

[Machine-readable sources](release-0.5.3-security-sources.json) retain eleven live
RustSec source blobs, nine GHSA endpoint cases and the eleven RustSec web-link
checks. All RustSec files and pages were available; eight GHSA records were
available. GHSA-jh2m-fhpj-3vr7 returned 404 from the global advisory endpoint: the
alias is explicitly present in the available RustSec 0486 source, so the notes
retain it without inventing an available GHSA page. RustSec 0381/0382 list no GHSA
alias and share CVE-2026-111943. No missing source was silently counted as verified.

All eight existing source tags from 0.1.0 through 0.5.2 lock rustls0.23.35,
rustls-webpki0.103.8, the advisory-bearing webpki-roots1.0.4 parent and rustix1.1.2.
That supports the upgrade boundary; it does not prove all issue paths are active.
The patched graph has rustls0.23.46, rustls-webpki0.103.17, webpki-roots1.0.10 and
rustix1.1.6, with libc/linux-raw-sys updates already accepted on main.

The locked rustls feature tree includes ring/std/tls12/logging, not Brotli or an
AWS-LC hybrid group. network.rs/publish.rs client builders do not configure CRLs.
Source checks found no custom ClientSessionStore, TLS session-value Debug
formatting, key logger or rustix xattr calls. Proxy credential Debug is redacted;
publication credentials are not Debug-formatted. These are named source/feature
bounds, not exploit tests or a universal claim for library consumers' feature graphs.

Official-origin/redirect restrictions and TLS verification limit reachable peers,
but cannot eliminate attacks on certificate validation itself. The notes explicitly
retain the distrusted/misissued-chain and network-position cases and do not call
checksums independent authentication when metadata and payload share a compromised
TLS channel. No exploit in rust-mirror was demonstrated by this qualification.

## Publication boundary

The selected publisher is .github/workflows/trusted-publishing.yml, environment
crates-io. After the coordinator merges the green release PR, create an annotated
tag at the exact merge; owner environment review gates the short-lived OIDC token.
No long-lived Cargo token, premerge tag, publication, asset upload or advisory
publication is part of candidate qualification. Five archives plus the SBOM make
six hashed payloads; SHA256SUMS is the seventh public file.

Actual registry checksum/payload vs merge, docs.rs, a fresh registry install,
committed GitHub Release notes, all provenance/SBOM bindings with the reusable
signer/source digest policy, public Windows/GNU/musl executions and the registry
workflow belong in a separate postpublication record PR. No SLSA3 badge is claimed
before that live verification. If owner review outlasts binary release waiting,
retry only the exact immutable-tag workflow with no existing assets; never replace
a successful prefix or move the tag. Old native kernels and arbitrary enterprise
NSS/proxy, client SDK and production-Nexus environments remain unqualified.
