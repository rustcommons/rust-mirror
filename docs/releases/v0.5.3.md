# rust-mirror 0.5.3

## Changes

This security patch updates the locked TLS/trust/filesystem dependencies already
merged in PR #51. No application implementation, CLI/library contract, protocol 1,
saved schema or Rust 1.90 MSRV change is introduced. Existing libc/linux-raw-sys
entries also advance as required by rustix; no new crate dependency names are added.

RustSec 0381/0382 share CVE-2026-111943 and list no GHSA alias at this audit.
For 0486, the alias above is present in the verified RustSec source; its GitHub
global-advisory endpoint returned 404 during qualification. The RustSec link is
the maintained primary reference, not a claim that that GHSA page was available.

The affected rust-mirror version range is **<= 0.5.2 when installed with its
shipped Cargo.lock (`cargo install --locked`) or obtained as a prebuilt download**.
All eight existing source tags lock rustls0.23.35, rustls-webpki0.103.8, the
webpki-roots1.0.4 parent and rustix1.1.2. This is a conservative upgrade boundary,
not a claim that every issue is exploitable on every target or feature graph.
Version 0.5.3 carries the patched lock. Installing older source without --locked,
or embedding the library, can resolve a different graph: inspect the application's
own lock/features rather than infer its dependency state from our version alone.

The CLI makes outbound HTTPS requests, not a public TLS server. Upstream downloads
are restricted to official origins, redirects are refused and TLS verification
remains enabled; publication uses an explicitly configured HTTPS destination.
These controls limit which peers are contacted, **not** all attacks on certificate
verification. A network-position attacker with an accepted misissued/distrusted
certificate can still matter, including the emSign paths described by 0381/0382.
Hashes checked against metadata from the same TLS connection are not independent
authentication if an attacker can replace both metadata and payload.

The shipped CLI's locked graph does not enable rustls Brotli; it uses the ring
provider without a hybrid post-quantum group. The audited client builders do not
configure CRLs. rust-mirror does not implement a custom ClientSessionStore, format
TLS session values with Debug, or install a key logger; credentials have redacted
Debug representations. Thus no rust-mirror session-secret debug-logging path was
identified for 0346, and the Brotli/CRL paths have specific configuration exclusions.
The audited source does not call rustix xattr functions. These are source/feature
observations, not exploit proofs or a blanket assertion that old releases are safe.
Library consumers may unify different features and must audit their own graph.
No exploitation of these dependencies in rust-mirror has been demonstrated here.

### Release automation and downloads

0.5.3 is the first release scheduled to use owner-approved crates.io Trusted
Publishing, through trusted-publishing.yml and the crates-io environment review.
No long-lived Cargo token is used. The prior owner-machine process remains available,
but is not the selected publication route for this release.

The five platform downloads remain Windows static CRT, Linux glibc 2.17, static
Linux musl, and macOS arm64/x86_64. They now also ship rust-mirror-0.5.3.cdx.json:
six payload assets plus one SHA256SUMS covering all six. All seven files receive
provenance from the reusable build-binaries.yml signer; each archive additionally
has a CycloneDX SBOM binding. The SBOM covers the frozen all-target Cargo dependency
graph, not OS runtimes, SDKs or CI tools. Windows release-only /Brepro accompanies
static CRT. Releases 0.5.1/0.5.2 and their signers/manifests remain unchanged.

## Upgrade

Install `cargo install rust-mirror --version 0.5.3 --locked`, or download and verify
the matching 0.5.3 archive using the install guide. Do not assume an existing binary
changes when its source repository's lock changes. Library consumers must also update their own affected transitive lock entries;
changing the rust-mirror dependency alone does not replace their application lock.
See [Cargo dependency updates](https://doc.rust-lang.org/cargo/reference/resolver.html#dependency-updates).
Omitting --locked is not an assurance of safety. No plan/catalog migration is
required. Default roots now exclude the distrusted emSign root; sites depending
on that chain need a legitimate replacement chain, not disabled TLS verification.

## Validation and limits

Qualification requires the exact-candidate five-target dry run, all eight GNU
userland launch/real HTTPS plan-sync gates, static/DLL/linkage checks, and six
payload hashes in one manifest. The package audit verifies clean VCS, allowed
members, normalized/original manifest, lock/source/license/README/changelog bytes,
and a fresh isolated install from the unpacked archive. Security gates fetch current
RustSec findings with no advisory ignores. Two-clean-build measurements retain
actual executable/archive/SBOM hashes; green CI alone is not a bit-identity claim.

Main's security-baseline native lifecycle, Cargo conformance and disposable
Linux/Windows Nexus evidence exercised this same patched dependency graph. Carry
that evidence only within its named bounds; this is not an exploit-validation or
arbitrary-project guarantee. Registry checksum/payload, docs.rs, registry install,
live reusable provenance/SBOM bindings and downloaded Windows/GNU/musl execution
are postpublication checks and are not claimed in advance. No SLSA3 badge is added
before actual live verification of the new signer.

GNU evidence covers the eight named container userlands on a modern host kernel,
not old native kernels or commercial SLES. For glibc below 2.17 use musl. Existing
proxy/NSS, arbitrary SDK/client-build, local-filesystem and production-Nexus limits
remain; no new platform or remote-pruning guarantee is introduced.
